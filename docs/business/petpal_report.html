1. วัตถุประสงค์ของเอกสาร

เอกสารนี้จัดทำขึ้นเพื่อ (1) แยกให้ชัดเจนว่าค่าใช้จ่ายส่วนใดเป็น "ค่าแรงพัฒนา" และส่วนใดเป็น "ค่าใช้จ่ายดำเนินการ (Infrastructure)" ที่ควรแยกออกจากงบพัฒนา (2) เสนอโครงสร้างราคากล้องสำหรับโรงแรมพันธมิตร (3) ประเมินความเสี่ยงด้าน bandwidth เมื่อจำนวนกล้อง/โรงแรมเพิ่มขึ้น พร้อมข้อเสนอ Mini Server Hub และ (4) วางแผนรองรับการขยายระบบทั้งฝั่ง Server และฝั่ง AI/LLM

2. แยกค่าใช้จ่าย: ค่าแรงพัฒนา vs ค่า Infrastructure

หลักการ: ค่าแรงพัฒนา (ออกแบบ UX/UI, เขียนโค้ด, เชื่อมต่อระบบ, ส่งขึ้น Store) ควรเป็นเงินที่ทีมพัฒนาได้รับเต็มจำนวน ส่วน ค่า Infrastructure คือต้นทุนดำเนินธุรกิจต่อเนื่องที่เกิดขึ้นไม่ว่าใครจะเป็นคนพัฒนาก็ตาม และเกิดขึ้นซ้ำทุกปี/ทุกเดือนตลอดอายุของแอป — จึงควรเป็นค่าใช้จ่ายที่ผู้ว่าจ้าง (เจ้าของโปรเจกต์) รับผิดชอบโดยตรง ไม่ใช่หักจากค่าแรงของทีมพัฒนา

2.3 ค่า Maintenance ระบบรายเดือน (สำหรับทีมพัฒนา)

งบ 20,000 บาทที่ตกลงกันเป็น ค่าแรงสร้างโปรเจกต์ครั้งเดียว (one-time) เท่านั้น แต่หลังส่งมอบงานแล้ว ระบบยังต้องการการดูแลต่อเนื่องจริง — เฝ้าระวังเซิร์ฟเวอร์, แก้บั๊กที่เจอหลังใช้งานจริง, อัปเดตความปลอดภัย, ต่ออายุ/จัดการ certificate, ดูแลเมื่อ Gemini หรือผู้ให้บริการภายนอกเปลี่ยนแปลง API (ดังที่เจอในหัวข้อ 5.2) งานส่วนนี้ไม่ควรรวมอยู่ในค่าแรงครั้งเดียว จึงเสนอให้เก็บเป็น ค่า Maintenance รายเดือนแยกต่างหาก จ่ายให้ทีมพัฒนาโดยตรง

แพ็กเกจราคา/เดือน (บาท)ขอบเขตงาน
Basic ~2,000–3,000 เฝ้าระวังระบบ (uptime monitoring), แก้บั๊กวิกฤต (server ล่ม/ล็อกอินไม่ได้), ต่ออายุ SSL/Apple Developer ให้ตรงเวลา
Standard ~4,000–6,000 รวม Basic + แก้บั๊กทั่วไปที่ลูกค้าแจ้ง + อัปเดตความปลอดภัย/dependency เป็นประจำ + ปรับแต่งเล็กน้อย (minor tweaks)
Growth ~8,000+ รวม Standard + feature เล็กใหม่ตามรอบ + ดูแลการ scale เมื่อผู้ใช้เพิ่ม (ตามหัวข้อ 5.1)
สำคัญ: ค่า Maintenance นี้เป็นคนละก้อนกับ Package รายเดือนที่โรงแรมจ่าย (หัวข้อ 3.2) — เงินจากโรงแรมคือรายได้ของธุรกิจ (ผู้ว่าจ้าง) ส่วนค่า Maintenance ในหัวข้อนี้คือค่าตอบแทนทีมพัฒนา ที่ผู้ว่าจ้างจ่ายให้ทีมเพื่อดูแลระบบต่อ ไม่ควรนำเงินก้อนเดียวกันมานับซ้อนเป็นทั้งสองอย่าง

2.4 ค่าธรรมเนียม Payment Gateway (Omise / Opn Payments)

ระบบจองจำเป็นต้องรับชำระเงินจริงผ่านช่องทางอิเล็กทรอนิกส์ หลังเปรียบเทียบผู้ให้บริการหลายเจ้า (Omise/Opn, Stripe, 2C2P) เลือกใช้ Omise (Opn Payments) เป็นเกตเวย์หลัก เพราะออกแบบมาสำหรับธุรกิจไทยที่มีหน้าร้านจริงโดยเฉพาะ, onboarding เร็ว, ไม่มีค่า setup/รายเดือน และรองรับทั้งบัตรเครดิต/เดบิตและ PromptPay ตั้งแต่วันแรก

ช่องทางชำระเงินค่าธรรมเนียมหมายเหตุ
บัตรเครดิต/เดบิต 3.65% (+VAT 7%) คิดจากยอดชำระต่อรายการ หักจากยอดที่โอนเข้าบัญชีเรา (net settlement)
PromptPay 1.65% (+VAT 7%) ถูกกว่าบัตรเกือบครึ่ง — คนไทยส่วนใหญ่นิยมใช้ช่องทางนี้อยู่แล้ว
ค่า setup / รายเดือน 0 Pay-as-you-go ไม่มีต้นทุนคงที่ก่อนเริ่มมีรายได้จริง
VAT 7% ในตารางนี้คือ VAT ของค่าบริการ gateway เท่านั้น (Omise เก็บจากเราในฐานะผู้ซื้อบริการ payment processing) เป็นต้นทุนภายในธุรกิจ ไม่ใช่ VAT ที่ต้องแจ้ง/เก็บจากลูกค้าปลายทาง — ลูกค้าเห็นแค่ยอดที่ต้องจ่ายเฉยๆ ส่วน VAT ของการขายบริการจริง (ถ้า PetPal หรือโรงแรมจดทะเบียน VAT แล้ว) เป็นคนละเรื่องกัน ต้องปรึกษานักบัญชีแยกต่างหากก่อน production

โมเดลที่เลือก: Absorb fee — PetPal รับต้นทุนค่าธรรมเนียม gateway เอง ผูกเข้าไปในค่าคอมมิชชั่นที่เก็บจากโรงแรม ไม่บวกเพิ่มเป็นรายการแยกให้ลูกค้าเห็นตอน checkout (เหมือนแอปจองที่พักส่วนใหญ่ในไทย) เพื่อให้ UX ง่าย ราคาเดียวจบ

3. โครงสร้างราคากล้องสำหรับโรงแรมพันธมิตร

3.1 ต้นทุนกล้อง

กล้อง (เช่น TP-Link Tapo C210) มีต้นทุนตัวละประมาณ 700–1,000 บาท — เสนอให้เป็นค่าใช้จ่ายที่ โรงแรม รับผิดชอบเอง ไม่ใช่ทีมพัฒนาหรือผู้ว่าจ้างกลาง เนื่องจากกล้องเป็นทรัพย์สินที่ติดตั้งอยู่ที่โรงแรม

3.2 โปรโมชั่นจูงใจโรงแรม (ตามที่หารือ)

เงื่อนไขรายละเอียด
กล้องตัวแรก ฟรี หรือส่วนลดพิเศษ (เลือกตามงบการตลาดของแพลตฟอร์ม) — ใช้จูงใจให้โรงแรมสมัครเข้าร่วมระบบ
กล้องตัวถัดไป ลด 30% จากราคาต้นทุน (~700–1,000 บาท) → โรงแรมจ่ายจริงประมาณ 490–700 บาท/ตัว
เงื่อนไขบังคับ ต้องสมัคร Package รายเดือน เพื่อครอบคลุมค่า Maintenance ระบบ (health check, ดูแล Mini Hub, ค่า backend ที่ให้บริการสตรีม)
ข้อเสนอราคาต่อเดือน (ตัวอย่างเริ่มต้น ให้ผู้ว่าจ้างปรับตามกลยุทธ์การตลาดจริง): คิดราคาแบบ "ต่อโรงแรม" ไม่ใช่ "ต่อกล้อง" (เช่น 199–299 บาท/เดือน/โรงแรม ไม่จำกัดจำนวนกล้องในแพ็กเกจพื้นฐาน) จะขายและอธิบายให้โรงแรมเข้าใจง่ายกว่าคิดราคาต่อกล้อง และยังจูงใจให้โรงแรมติดกล้องเพิ่มโดยไม่ต้องกังวลค่า subscription ที่เพิ่มตาม

4. การประเมินด้านเทคนิค: Bandwidth และสถาปัตยกรรมกล้อง

4.1 สถาปัตยกรรมปัจจุบัน — ข้อจำกัดที่สำคัญกว่าเรื่อง bandwidth

ปัจจุบันแอปฝั่งลูกค้าเชื่อมต่อกับกล้องแบบ ตรงไปยัง IP ภายในเครือข่าย (LAN) ของโรงแรมเลย ไม่ได้ผ่าน backend กลางในการส่งวิดีโอ (backend ทำหน้าที่แค่ตรวจสิทธิ์และส่ง URL ให้)

ข้อจำกัดสำคัญ: ด้วยสถาปัตยกรรมนี้ ลูกค้าที่ไม่ได้เชื่อมต่อ WiFi เดียวกับโรงแรมจะดูกล้องไม่ได้เลย เพราะ IP ภายใน (LAN) ไม่สามารถเข้าถึงได้จากอินเทอร์เน็ตภายนอก — และไม่ควรแก้ด้วยการเปิด Port Forward กล้องออกสู่อินเทอร์เน็ตตรงๆ เพราะเสี่ยงต่อการถูกโจมตี/แฮกกล้องจากภายนอกสูงมาก จึงไม่ใช่แค่เรื่อง bandwidth แต่เป็นเงื่อนไขที่ทำให้ฟีเจอร์ "ดูกล้องลูกจากที่ไหนก็ได้" ยังใช้งานได้จริงแค่ในวงจำกัด (ต้องอยู่ในโรงแรมเท่านั้น)

4.2 หาก Scale ขึ้น: ปัญหา Bandwidth ที่จะตามมา

ในระยะยาว เมื่อระบบรองรับการดูข้ามเครือข่ายได้ (ผ่าน backend กลางหรือ Mini Hub) วิดีโอจะต้อง "ไหล" ผ่านสายใดสายหนึ่งจริง ประเด็นคือ จะให้ไหลผ่านที่ไหน:

  • ถ้าไหลผ่าน VPS กลาง: bandwidth ขาออกของ VPS ต้องรองรับทุกกล้องทุกโรงแรมที่มีคนดูพร้อมกัน ประมาณการคร่าวๆ ที่ sub-stream (720p H.264) กินราว 1–2 Mbps ต่อสาย (ตัวเลขประมาณอุตสาหกรรม — แนะนำวัดจริงด้วย ffprobe ที่ทีมมีเครื่องมืออยู่แล้วเพื่อความแม่นยำ) หากมี 20 โรงแรมดูพร้อมกัน 20 สาย จะกิน bandwidth ต่อเนื่อง ~20–40 Mbps ซึ่งเกินแพ็กเกจเน็ตของ VPS ราคาประหยัดทั่วไปได้ง่าย เมื่อจำนวนโรงแรม/กล้องโตขึ้น ต้นทุนและความเสี่ยงคอขวดจะอยู่ที่ VPS ศูนย์กลางจุดเดียว
  • ถ้าไหลผ่าน Mini Hub ที่แต่ละโรงแรม: bandwidth ขาออกของสตรีมจะไปตกอยู่ที่อินเทอร์เน็ตของโรงแรมนั้นๆ เอง (ซึ่งควรมีอยู่แล้วเพื่อใช้งานทั่วไป) ทำให้ต้นทุน/ภาระกระจายตามจำนวนโรงแรม ไม่รวมศูนย์ที่ VPS เดียว
ข้อควรเข้าใจตรงกัน: กล้อง (Tapo) ไม่ได้ "อัปโหลดขึ้นคลาวด์" เองทั้งในสถาปัตยกรรมปัจจุบันและแผน Mini Hub — กล้องแค่เปิด RTSP อยู่ในเครือข่าย LAN ของโรงแรมเท่านั้น การ "อัปคลาวด์" มีเฉพาะกรณีเปลี่ยนไปใช้กล้อง EZVIZ (หัวข้อ 4.4) เท่านั้น ส่วน Mini Hub คือเครื่องที่โรงแรมดึงสตรีมจากกล้องในเครือข่ายเดียวกัน (เฉพาะตอนมีคนดูจริง) แล้วส่งออกผ่าน Tailscale ไปหา backend กลาง — ดังนั้น Mini Hub ไม่ได้ลด bandwidth รวมของระบบ เพียงแต่ย้ายภาระจาก "VPS กลางจุดเดียวแบกทุกโรงแรม" ไปเป็น "แต่ละโรงแรมรับผิดชอบ bandwidth ของกล้องตัวเอง" ทำให้ไม่มีจุดคอขวดเดียวที่ต้องอัปเกรดตามจำนวนโรงแรมที่โต

4.2.1 ประมาณการความจุ VPS ที่กำลังพิจารณา (5 vCPU / 10GB / 1000 Mbps Shared)

ที่ sub-stream ~1-2 Mbps/สาย (ยังไม่ได้วัดจริงด้วย ffprobe) พอร์ต 1000 Mbps รองรับได้ตามทฤษฎีสูงสุด ~650 สายพร้อมกัน — เกินความต้องการช่วงเริ่มต้น/กลางมาก (20 โรงแรมพร้อมกัน ≈ 20-40 Mbps เท่านั้น ตามหัวข้อ 4.2) แต่ตัวเลข 650 เป็นแค่ลิมิตทางทฤษฎีจากความเร็วพอร์ตอย่างเดียว ปัจจัยที่จะติดจริงก่อนมีดังนี้:

ปัจจัยจำกัดจริงรายละเอียด
Shared bandwidth พอร์ตแชร์กับ VPS อื่นบนเครื่องเดียวกัน ช่วง peak อาจได้ไม่ถึง 1000 Mbps เต็ม ควรประเมินแบบระมัดระวังที่ ~50-70% ของสเปก
Monthly data transfer quota ยังไม่ทราบโควตาที่แน่ชัดจากผู้ให้บริการ — ต้องยืนยันก่อนสมัคร ตัวอย่างประมาณการ (ที่ 1.5 Mbps/สาย): 20 โรงแรม ดูเฉลี่ย 2 ชม./วัน ≈ 800 GB/เดือน, ถ้า peak 4 ชม./วัน ≈ 1.6 TB/เดือน
CPU/RAM ของ backend ถ้า backend ต้องประมวลผลสตรีม (เช่น แปลง RTSP→WebRTC) มากกว่าแค่ proxy เฉยๆ อาจติดคอขวดที่ CPU ก่อนถึงลิมิต network เมื่อจำนวนสายพร้อมกันเพิ่มขึ้น
ตัวเลขในตารางนี้เป็นการประมาณการเพื่อวางแผนงบเบื้องต้นเท่านั้น ควรวัด bitrate จริงของกล้อง Tapo ด้วย ffprobe และสอบถามผู้ให้บริการ VPS เรื่อง data transfer quota ก่อนตัดสินใจสมัครแพ็กเกจจริง

4.3 ข้อเสนอ: Mini Server Hub ต่อโรงแรม

สอดคล้องกับสิ่งที่เสนอมา — แนะนำให้แต่ละโรงแรมมี "Hub" ขนาดเล็ก (เช่น Raspberry Pi หรือมินิคอมพิวเตอร์ราคาประมาณ 1,500–3,000 บาท ซื้อครั้งเดียว) ทำหน้าที่:

  1. ดึงสตรีมจากกล้องทุกตัวในโรงแรมนั้น เฉพาะตอนมีคนดูจริง (on-demand ตามหลักการที่วางไว้แต่ต้น — ไม่ดึงสตรีมค้างตลอดเวลา)
  2. ส่งสตรีมออกผ่าน Tailscale แบบ outbound-only ไปหา backend กลาง (ไม่ต้องเปิด port ใดๆ ให้โรงแรม ปลอดภัยกว่าการ port-forward กล้องตรง)
  3. backend กลางทำหน้าที่แค่ตรวจสิทธิ์ + ส่งต่อสัญญาณ (ไม่ต้องแบก bandwidth วิดีโอเองทั้งหมด)

หมายเหตุ: สถาปัตยกรรมนี้ตรงกับแผนระยะยาวที่วางไว้ในเอกสารออกแบบระบบกล้องอยู่แล้ว (edge server phase) เพียงแต่ยังไม่ได้ลงมือสร้างจริง เป็นงานที่ควรวางแผนเป็นเฟสถัดไปเมื่อเริ่มมีโรงแรมที่ต้องการให้ลูกค้าดูจากนอกสถานที่ ไม่จำเป็นต้องทำตั้งแต่วันแรกที่ยังมีโรงแรมทดสอบไม่กี่แห่ง

4.4 ทางเลือก: เปลี่ยนยี่ห้อกล้องแทนการสร้าง Mini Hub เอง

สำรวจแล้วว่ามีกล้องยี่ห้อไหนที่มี "Developer / Business API" ให้ third-party app อย่าง PetPal เรียกดูสตรีมได้โดยตรง โดยไม่ต้องสร้าง Edge Hub เอง — พบ 3 แพลตฟอร์มหลัก ผลสรุปคือไม่ได้ถูกกว่าอย่างที่คาดในทุกกรณี รายละเอียดตามนี้:

แต่ — "เปลี่ยนกล้องถูกกว่า" ไม่จริงเสมอไป: EZVIZ คิดค่าบริการรายปีต่อกล้องตลอดไป ในขณะที่แผน Mini Hub (หัวข้อ 4.3) เป็นค่าใช้จ่ายครั้งเดียวต่อโรงแรม (ไม่ใช่ต่อกล้อง) ลองเทียบที่โรงแรมเฉลี่ย 3 กล้อง/แห่ง:
  • EZVIZ: ~480 บาท/ปี/โรงแรม ตลอดไป (ปีที่ 5 จ่ายไปแล้ว ~2,400 บาท)
  • Mini Hub: ~1,500–3,000 บาท ครั้งเดียว ต่อโรงแรม ใช้ได้หลายปี
จุดคุ้มทุนอยู่ที่ปีที่ 3-4 หลังจากนั้น Mini Hub ถูกกว่าแน่นอน — EZVIZ ยังมีข้อเสียเพิ่มคือวิดีโอสัตว์เลี้ยง/ห้องพักลูกค้า ต้องวิ่งผ่าน server ของ EZVIZ ก่อนถึงเรา (เรื่อง privacy ต้องแจ้งลูกค้า/โรงแรมให้ทราบ) ในขณะที่ Mini Hub เก็บวิดีโอไว้ในระบบของเราเองทั้งหมด

ข้อสรุป: แนะนำให้ คง Tapo เดิมไว้ + สร้าง Mini Hub เอง เป็นแผนหลัก (คุ้มค่ากว่าระยะยาว, privacy ดีกว่า, ไม่ผูกกับผู้ให้บริการภายนอก) — เก็บ EZVIZ ไว้เป็นแผนสำรองเฉพาะกรณีที่ต้องการเปิดฟีเจอร์ "ดูนอกโรงแรม" ให้เร็วที่สุด โดยยังไม่มีเวลา/กำลังคนสร้าง Mini Hub ในเฟสนี้

4.5 ถ้าเลือก EZVIZ: ผลต่อค่า Infrastructure ที่ต้องตั้งงบเพิ่ม

เส้นทางวิดีโอของ EZVIZ ไหลจาก กล้อง → EZVIZ cloud → มือถือลูกค้า โดยตรง — VPS กลางของเรา (หัวข้อ 2.1) ไม่ต้องรับ-ส่งไฟล์วิดีโอแม้แต่ byte เดียว ต่างจากแผน Mini Hub ที่วิดีโอยังไหลผ่าน backend กลางอยู่บางส่วน ข้อดีคือค่า VPS ไม่ต้องปรับขึ้นตามจำนวนกล้อง/โรงแรมเลย ไม่ว่าจะมีกี่สายดูพร้อมกัน — แต่ bandwidth ไม่ได้หายไป แค่ย้ายไปเป็นบิลของ EZVIZ แทน จึงต้องตั้งเป็นค่า Infrastructure บรรทัดใหม่แยกต่างหาก ไม่ใช่ค่า VPS เดิม

รายการประมาณการเงื่อนไข
ค่าอุปกรณ์ต่อกล้อง $4.5/ตัว/ปี (~160 บาท) เฉพาะจำนวนกล้องที่เกิน free quota ของบัญชี (ยังไม่ทราบจำนวนฟรีที่แน่ชัด — ต้องถาม EZVIZ ตรงๆ ก่อนตั้งงบจริง)
ค่า bandwidth ส่วนเกิน $0.4/GB ตัวอย่างประมาณการ (ไม่ใช่ตัวเลขยืนยันจาก EZVIZ): ถ้าลูกค้าดูกล้องรวมกันทั้งระบบ ~100 ชม./เดือน ที่ sub-stream ~1.5 Mbps ≈ ใช้ data ~66 GB/เดือน → หากเกิน quota ฟรีทั้งหมดจะอยู่ราว $26/เดือน (~950 บาท/เดือน)
ข้อจำกัด free tier 3 สายพร้อมกัน บัญชีฟรีรองรับแค่ 3 การดูพร้อมกันทั้งระบบ — ถ้าลูกค้าดูพร้อมกันเกินนี้ต้องอัปเกรด tier (ราคาอัปเกรดยังไม่ยืนยัน)
ตัวเลขในตารางนี้เป็นการประมาณการเพื่อใช้วางแผนงบเบื้องต้นเท่านั้น ไม่ใช่ราคาที่ยืนยันจาก EZVIZ โดยตรง — ก่อนตัดสินใจใช้จริงควรติดต่อฝ่ายขาย EZVIZ Open Platform เพื่อขอราคา/quota ที่แน่นอนสำหรับจำนวนกล้องและปริมาณการใช้งานจริงของ PetPal

5. แผนรองรับการขยายระบบ (Scaling Plan)

5.1 Server Scaling

ระยะแนวทาง
ระยะเริ่มต้น (ปัจจุบัน) VPS เดียว 4 vCPU/8GB รองรับ Postgres, MinIO, LiveKit, Redis, Backend ในเครื่องเดียวได้สบาย
เมื่อผู้ใช้เพิ่มขึ้น ขยายแนวตั้ง (vertical scale) — อัปเกรดแพ็กเกจ VPS ที่ใหญ่ขึ้นก่อน เป็นวิธีที่เร็วและถูกที่สุดสำหรับ scale ระดับต้น
ข้อควรระวังก่อน scale แนวนอน (หลาย instance) ระบบจำกัดจำนวนคำขอ (rate limiter) ปัจจุบันเก็บสถานะไว้ในหน่วยความจำของเครื่องเดียว ถ้าในอนาคตต้องเพิ่ม backend มากกว่า 1 เครื่องพร้อมกัน ต้องย้าย logic นี้ไปใช้ Redis ก่อน (ระบบมี Redis ใช้งานอยู่แล้วสำหรับ AI job queue จึงต่อยอดได้ทันที ไม่ต้องเพิ่มเทคโนโลยีใหม่)
ฐานข้อมูล (Postgres + pgvector) รองรับ scale ระดับ startup ได้อีกนาน ยังไม่จำเป็นต้องวางแผน replica/cluster จนกว่าจะมีผู้ใช้จำนวนมากจริง

Prompt caching (ทั้ง Gemini และ Claude) ช่วยลดต้นทุนได้เพิ่มเติมถ้า context ที่ส่งซ้ำๆ (เช่น รายละเอียดโรงแรมที่ไม่เปลี่ยนบ่อย) ถูกแคชไว้ — Claude คิดค่า cache read ที่ ~10% ของราคาปกติ ยังไม่ได้นำมาคำนวณในตัวเลขข้างต้นเพื่อความง่าย

5.3 ตัวอย่างประมาณการค่าใช้จ่ายรวมรายเดือน (Payment Gateway + LLM) ตามขนาดลูกค้า

เพื่อให้เห็นภาพว่าต้นทุนผันแปร (variable cost) จะเป็นเท่าไหร่เมื่อธุรกิจโต จำลอง 3 สถานการณ์ตามปริมาณการจองและการใช้ AI Smart Match สมมติฐาน: มูลค่าเฉลี่ยต่อการจอง ~2,000 บาท, สัดส่วนช่องทางชำระเงิน PromptPay 70% / บัตร 30% (ค่าธรรมเนียมเฉลี่ยถ่วงน้ำหนัก ~2.41% รวม VAT ของ gateway), และประมาณ 1,200 input token + 350 output token ต่อคำขอ AI Smart Match หนึ่งครั้ง

สถานการณ์จองงาน/เดือนคำขอ AI/เดือนค่า Omise/เดือนค่า LLM (Gemini)ค่า LLM (Claude Haiku 4.5)
เริ่มต้น (Pilot) 30 500 ~1,450 บาท 0 บาท (ในโควตาฟรี) ~53 บาท
เติบโต (Growth) 300 10,000 ~14,500 บาท 0 บาท (ในโควตาฟรี) ~1,060 บาท
ขยายเต็มระบบ (Scale) 2,000 80,000 (~2,700/วัน) ~96,400 บาท ~330 บาท (เกินโควตาฟรีบางส่วน) ~8,500 บาท
ข้อสังเกตสำคัญ: ในทุกสถานการณ์ ค่าธรรมเนียม Payment Gateway (Omise) เป็นต้นทุนผันแปรหลักที่ครองสัดส่วนสูงสุดเสมอ (สูงกว่าค่า LLM แม้เป็น Claude หลายสิบเท่าตัว) เพราะคิดเป็น % ของมูลค่าเงินที่ไหลผ่านระบบทั้งหมด ไม่ใช่ต่อ "การเรียกใช้งาน" แบบ AI ดังนั้นแม้จะยอมจ่ายแพงขึ้นเพื่อสลับไปใช้ Claude เพื่อคุณภาพที่ดีกว่า ผลกระทบต่องบรวมรายเดือนก็ยังค่อนข้างจำกัดเมื่อเทียบกับค่า gateway

ตัวเลขข้างต้นเป็นการประมาณการเพื่อวางแผนงบเบื้องต้นเท่านั้น (ไม่รวมผลจาก prompt caching ที่จะลดค่า LLM ลงได้อีก) ควรวัด token จริงจาก prompt ที่ใช้งานจริงด้วย token counting API ก่อนตั้งงบจริง

6. สรุปงบประมาณโดยรวม (ปีแรก)

หมวดจำนวนเงิน (บาท)ผู้รับผิดชอบ
ค่า Infrastructure (Server + Apple + Google) ~11,100 ผู้ว่าจ้าง
ค่ากล้อง (ต้นทุน 700–1,000/ตัว หักส่วนลดตามโปรโมชั่น) ตามจำนวนกล้องจริง โรงแรม
ค่าแรงพัฒนา (UX/UI + Dev 2 คน + Deploy Store) — ครั้งเดียว งบที่ตกลงกันไว้ (เช่น 20,000) ทีมพัฒนา
ค่า Maintenance ระบบ — รายเดือน ต่อเนื่องหลังส่งมอบ ~2,000–8,000+ /เดือน ทีมพัฒนา

7. ภาพรวมตลาด Pet Hotel ในประเทศไทย

ข้อมูลอ้างอิงต่อไปนี้รวบรวมจากรายงานตลาดสาธารณะ ใช้ประกอบการวางแผนธุรกิจ ไม่ใช่ตัวเลขที่ PetPal เก็บเอง — ควรใช้เป็นบริบทกว้างๆ ของทิศทางตลาด ไม่ใช่ตัวเลขที่แม่นยำระดับที่ใช้ตัดสินใจลงทุนได้ทันที

7.1 ขนาดตลาดและการเติบโต

รายการตัวเลข
ตลาด Pet Boarding Services ในไทย ~86.8 ล้านดอลลาร์สหรัฐ (2567/2024) → คาดการณ์ 164.2 ล้านดอลลาร์ภายในปี 2573/2030 (CAGR ~11.3% ช่วง 2568-2573)
ตลาด Pet Care โดยรวมในไทย (กว้างกว่า boarding) ~2.05 พันล้านดอลลาร์ → คาดการณ์ 4.03 พันล้านดอลลาร์ภายในปี 2575/2032 (CAGR ~10.14%)
มูลค่าตลาดสัตว์เลี้ยงไทยโดยรวม (หน่วยบาท) ~92,000 ล้านบาท (2568/2025, โต +13% จากปีก่อน) — คาดว่าจะทะลุ 100,000 ล้านบาทภายในปี 2569/2026
สัดส่วนตามประเภทสัตว์เลี้ยง สุนัขครองส่วนแบ่งรายได้สูงสุดในตลาด boarding (~89.9% ปี 2567) แต่แมวเป็นกลุ่มที่โตเร็วที่สุด

7.2 จำนวนสัตว์เลี้ยงและพฤติกรรมการใช้จ่าย

รายการตัวเลข
จำนวนสัตว์เลี้ยงในไทย สุนัขเลี้ยง ~3.45 ล้านตัว, แมวเลี้ยง ~1.94 ล้านตัว (ข้อมูล Kasikorn Research, 2568/2025)
จำนวนสัตว์เลี้ยงรวมทุกประเภท ~5.08 ล้านตัว (สำรวจโดยคณะสัตวแพทยศาสตร์ ม.เกษตรศาสตร์ ปี 2567/2024) เพิ่มขึ้น ~8% จากปีก่อนหน้า
ค่าใช้จ่ายเฉลี่ยต่อสัตว์เลี้ยงต่อปี ~50,500 บาท/ตัว/ปี (โต +23% จากปีก่อน) — เจ้าของบางส่วนใช้จ่าย $300-600/ปี โดยเฉพาะบริการอาบน้ำตัดขน
ข้อจำกัดของข้อมูล: ไม่พบสถิติสาธารณะที่ระบุความถี่การใช้บริการโรงแรมสัตว์เลี้ยงโดยตรง (เช่น จำนวนคืนเข้าพักเฉลี่ยต่อปีต่อครัวเรือน) ตัวเลขข้างต้นเป็นภาพรวมระดับตลาด/อุตสาหกรรมเท่านั้น หากต้องการข้อมูลความถี่การใช้งานที่แม่นยำ แนะนำให้เก็บข้อมูลจากการใช้งานจริงของ PetPal เอง หลังเปิดให้บริการระยะหนึ่ง หรือสำรวจโรงแรมพันธมิตรที่เข้าร่วมโดยตรง

แหล่งข้อมูล: Grand View Research (Thailand Pet Boarding Services Market, Thailand Pet Services Market), Kasikorn Research Center, สำรวจโดยคณะสัตวแพทยศาสตร์ มหาวิทยาลัยเกษตรศาสตร์ (2567/2024), Chiang Rai Times — ตัวเลขทั้งหมดเป็นข้อมูล ณ เวลาที่รวบรวม (กรกฎาคม 2569/2026) อาจมีการปรับปรุงจากผู้จัดทำรายงานต้นทางในภายหลัง

เอกสารฉบับนี้จัดทำขึ้นเพื่อการหารือระหว่างทีมพัฒนาและผู้ว่าจ้าง — ตัวเลขราคากล้อง/แพ็กเกจรายเดือนเป็นข้อเสนอเบื้องต้น สามารถปรับตามกลยุทธ์ทางธุรกิจจริง
