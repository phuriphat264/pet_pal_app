สลับ video player: flutter_vlc_player → media_kit

02 — ด่วน

พูดเรื่องนี้ก่อนเรื่องอื่นทั้งหมด

เจอระหว่างเตรียมเอกสารนี้ — ควรเป็นหัวข้อแรกที่คุยกับทีม เพราะฟีเจอร์กำลัง fail อยู่จริงในตอนนี้

🔴 Gemini model ที่ใช้อยู่ถูกยกเลิกไปแล้ว

backend/app/gemini_client.py:11 ตั้งค่า MODEL_NAME = "gemini-2.0-flash" — โมเดลนี้ Google ยกเลิกไปแล้วตั้งแต่ 1 มิ.ย. 2026 ฟีเจอร์ AI Smart Match enrichment น่าจะเรียก API แล้ว fail อยู่ในตอนนี้จริงๆ ต้องเปลี่ยนเป็น gemini-2.5-flash-lite (ราคาเท่าเดิม ไม่กระทบงบ)

สังเกตแปลก: commit ล่าสุดของ branch (1cad3e1 — Switch Gemini model to 2.0-flash) เพิ่งสลับกลับไปใช้โมเดลนี้ด้วยเหตุผลเรื่อง free quota — โดยไม่รู้ว่าโมเดลถูกเลิกใช้ไปแล้ว ควรเช็คกับทีมว่าใครเป็นคนแก้ล่าสุด และยืนยันให้ใช้ gemini-2.5-flash-lite แทนให้ตรงกัน

03 — เรื่องกล้อง

เปลี่ยนยี่ห้อกล้อง หรือสร้าง Mini Hub เอง?

ข้อจำกัดปัจจุบัน: แอปต่อกล้องแบบ RTSP ตรงไปยัง LAN IP ของโรงแรม — ลูกค้าที่ไม่ได้อยู่ใน WiFi โรงแรม ดูกล้องไม่ได้เลย สำรวจแล้วว่ามีทางแก้ 2 ทาง

แพลตฟอร์มสถานะสำหรับ Startup งบจำกัดต้นทุน
Tuya IoT Platformตัดออก commercial license แยกต่างหาก~180,000 บาท/ปีแรก
Tapo Open API ใช้อยู่ตอนนี้ตัดออก เปิดเฉพาะพาร์ทเนอร์ระดับ Amazon/Googleไม่เปิดขายให้ startup
Reolink RTMPตัดออก ยัง URL เป็น local IP เหมือนเดิม ไม่แก้ปัญหาจริง—
EZVIZ Open Platformใช้ได้จริง ออกแบบมาสำหรับ third-party business~$4.5/กล้อง/ปี + $0.4/GB

เทียบต้นทุนต่อโรงแรม (เฉลี่ย 3 กล้อง/แห่ง)

~480.-
EZVIZ ต่อปี/โรงแรม ตลอดไป — ปีที่ 5 จ่ายสะสมแล้ว ~2,400 บาท
~1,500–3,000.-
Mini Hub ครั้งเดียว/โรงแรม ใช้ได้หลายปี — คุ้มทุนปีที่ 3-4
ข้อเสนอ

คง Tapo เดิม + สร้าง Mini Hub เอง เป็นแผนหลัก (คุ้มค่ากว่าระยะยาว, privacy ดีกว่าเพราะวิดีโอไม่ต้องผ่าน cloud คนอื่น, ไม่ผูกกับผู้ให้บริการภายนอก) — เก็บ EZVIZ ไว้เป็นแผนสำรอง เฉพาะกรณีต้องรีบเปิดฟีเจอร์ "ดูนอกโรงแรม" ให้เร็วที่สุดโดยยังไม่มีเวลา/กำลังคนสร้าง Mini Hub

04 — Infra & ต้นทุน

อะไรควรแยกไปให้ผู้ว่าจ้างจ่ายเอง

หลักการ: ค่าแรงพัฒนา (ออกแบบ, เขียนโค้ด, เชื่อมต่อระบบ) ควรเป็นเงินที่ทีมได้เต็มจำนวน ส่วนค่า Infrastructure คือต้นทุนดำเนินธุรกิจต่อเนื่อง เกิดซ้ำทุกปี/เดือนไม่ว่าใครพัฒนา — ควรเป็นของผู้ว่าจ้างโดยตรง ไม่หักจากค่าแรงทีม

รายการค่าใช้จ่ายความถี่ผู้รับผิดชอบ
VPS Server (4 vCPU/8GB)440/เดือนรายเดือน/ปีผู้ว่าจ้าง
Apple Developer Program~3,600/ปีต่ออายุทุกปีผู้ว่าจ้าง
Google Play Console~900ครั้งเดียวตลอดชีพผู้ว่าจ้าง
Domain name (.com/.app)~400–800/ปีต่ออายุทุกปีผู้ว่าจ้าง
กล้องต้นทุน (700–1,000/ตัว)ตามจำนวนจริงตามการขยายโรงแรม

ค่า Maintenance รายเดือน — งบ 20,000 ที่ตกลงกันไว้เป็นค่าแรงสร้างโปรเจกต์ ครั้งเดียว เท่านั้น หลังส่งมอบแล้วระบบยังต้องเฝ้าระวังเซิร์ฟเวอร์ แก้บั๊ก ต่ออายุ certificate — ควรแยกเป็นค่า Maintenance รายเดือนต่างหาก จ่ายให้ทีม dev โดยตรง (คนละก้อนกับ package ที่โรงแรมจ่ายในหัวข้อราคากล้อง)

แพ็กเกจราคา/เดือนขอบเขต
Basic~2,000–3,000Uptime monitoring, แก้บั๊กวิกฤต, ต่ออายุ SSL/Apple Dev
Standard~4,000–6,000รวม Basic + แก้บั๊กทั่วไป + อัปเดต dependency ประจำ
Growth~8,000+รวม Standard + feature เล็กใหม่ตามรอบ + ดูแลการ scale

05 — เซิร์ฟเวอร์

จะเลือกตัวไหน และขยายยังไงเมื่อโตขึ้น

1

ตอนนี้: VPS เดียว 4 vCPU/8GB

รองรับ Postgres, MinIO, LiveKit, Redis, Backend ในเครื่องเดียวได้สบาย (~440 บาท/เดือน)

2

เมื่อ user เพิ่มขึ้น: ขยายแนวตั้งก่อน

อัปเกรดแพ็กเกจ VPS ให้ใหญ่ขึ้น — เร็วและถูกที่สุดสำหรับ scale ระดับต้น

!

ก่อนจะขยายแนวนอน (หลาย instance)

ต้องย้าย rate limiter จาก in-memory ไปใช้ Redis ก่อน (core/rate_limit.py) — Redis มีอยู่แล้วในระบบ ไม่ต้องเพิ่มเทคโนโลยีใหม่

ถ้ากล้องต้อง scale ข้ามเครือข่ายในอนาคต — bandwidth วิดีโอจะไหลผ่านที่ไหนมีผล:

เส้นทางผลต่อ VPS
ผ่าน VPS กลาง20 โรงแรมดูพร้อมกัน ≈ 20–40 Mbps ขาออก — คอขวดต้นทุนอยู่ที่ VPS จุดเดียว
ผ่าน Mini Hub ต่อโรงแรมbandwidth กระจายไปที่เน็ตของแต่ละโรงแรมเอง — ไม่รวมศูนย์ที่ VPS เดียว

06 — ถามทีม

งานที่จะชวนเพื่อนรับไปทำ + คำถามที่ต้องถามตรงๆ

งานฝั่งกล้องที่ยังไม่ได้ลงมือจริง (เฟสถัดไป) — เสนอให้เพื่อนเลือกได้ว่าจะรับส่วนไหน

Mini Server Hub ต่อโรงแรม

Raspberry Pi ดึงสตรีมกล้อง on-demand → ส่งผ่าน Tailscale outbound-only ไป backend กลาง — แก้ปัญหา "ดูกล้องนอกโรงแรมไม่ได้"

ยังไม่เริ่ม

Edge-server proxy สำหรับ RTSP credential

ตอนนี้ _build_stream_url ส่ง rtsp://user:pass@ip ตรงถึง client — ควรมี short-lived token ก่อนขึ้นโปรดักชันจริง

ควรทำก่อนโปรดักชัน

ตั้ง CI (GitHub Actions)

เทสที่มีอยู่ ~24 ไฟล์ ไม่ได้รันอัตโนมัติเลยตอน push/PR — ต้องรันมือทุกครั้ง

ยังไม่เริ่ม
