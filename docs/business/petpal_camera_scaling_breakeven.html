PetPal — กล้องรุ่นใหม่, แผน Scale Server และจุดคุ้มทุน Subscription ช่าง

อัปเดตต่อเนื่องจากเอกสาร "PetPal — เอกสารประเมินโปรเจกต์ & ข้อเสนอแยกค่าใช้จ่าย Infrastructure"
จัดทำ 18 กรกฎาคม 2569 (2026-07-18) · สำหรับผู้ว่าจ้าง/เจ้าของโปรเจกต์ — เอกสารนี้เป็นการประมาณการเพื่อวางแผน ไม่ใช่ตัวเลขยืนยันขั้นสุดท้าย

สรุปเร็ว: เปลี่ยนกล้องรุ่นใหม่ มีผลกับ Server ที่เช่าไหม?

  • ตัวกล้องเองแทบไม่มีผล ตราบใดที่ยังใช้ sub-stream ความละเอียดต่ำเหมือนเดิม (~720p, ~1.5 Mbps/สาย) ปัจจุบันแอปฝั่งลูกค้ายังเชื่อมต่อกล้องตรงผ่าน LAN ของโรงแรม — วิดีโอไม่ได้วิ่งผ่าน VPS ที่เช่าอยู่เลยสักบิตเดียวในตอนนี้
  • โดยหลักการแล้ว bandwidth ควรตกอยู่ที่เน็ตของโรงแรม ไม่ใช่ VPS — ถ้าออกแบบให้ Mini Hub ที่โรงแรมส่งวิดีโอตรง (peer-to-peer) ไปหามือถือลูกค้าได้สำเร็จ VPS กลางจะไม่แบกวิดีโอเลยจริงๆ
  • แต่มีข้อจำกัดทางเทคนิคหนึ่งจุดที่ทำให้บาง connection ต้อง "แวะ" ผ่าน VPS: Edge server ที่โรงแรมถูกออกแบบให้ซ่อนอยู่หลัง Tailscale โดยตั้งใจ (ห้ามเปิด port ออก public internet เพื่อความปลอดภัย) แต่มือถือลูกค้าไม่ได้อยู่ใน Tailscale network เดียวกัน จึงต่อตรงเข้า edge server ไม่ได้เสมอไป — WebRTC จะพยายามต่อ P2P ก่อน แล้ว "fallback" ไปใช้ relay กลางเฉพาะตอนต่อตรงไม่สำเร็จ (พบบ่อยเวลาลูกค้าใช้เน็ตมือถือหลัง CGNAT ซึ่งในไทยค่อนข้างเยอะ) จุด relay นั้นแหละที่กลายเป็นภาระของ VPS ได้ ถ้าเรารัน relay อยู่บนเครื่องเดียวกับ backend
  • สรุป: Mini Server Hub ยังคงเป็นคำตอบที่ถูกต้อง เพราะลดสัดส่วนวิดีโอที่ต้องพึ่ง VPS ลงมาก (เหลือเฉพาะส่วนที่ P2P ต่อตรงไม่สำเร็จ) แต่ไม่ได้ทำให้เหลือ 0% เป๊ะ — กราฟหัวข้อ 1 ปรับให้สะท้อนสัดส่วนนี้แล้ว แทนที่จะสมมติว่าเป็น 0 บาทเสมอ

1. ถ้าดูพร้อมกันหลายโรงแรม Server จะเป็นอย่างไร

มี 2 เส้นทางที่วิดีโอจะไหลผ่านได้ เมื่อระบบขยายให้ดูข้ามเครือข่ายได้ (ตามหัวข้อ 4.2–4.3 ในเอกสารเดิม):

  • ไม่มี Mini Hub — ไหลผ่าน VPS กลางทั้งหมด: bandwidth ขาออกของ VPS ต้องรองรับทุกกล้องทุกโรงแรมที่มีคนดูพร้อมกัน 100% เมื่อจำนวนสายพร้อมกันเพิ่มขึ้น ต้องอัปเกรด VPS เป็นแพ็กเกจที่ใหญ่ขึ้นเป็นขั้นบันได (step) — ต้นทุนและจุดคอขวดอยู่ที่ VPS เครื่องเดียว
  • มี Mini Hub ต่อโรงแรม: วิดีโอส่วนใหญ่พยายามวิ่งตรง (WebRTC peer-to-peer) จาก Mini Hub ไปหามือถือลูกค้า — bandwidth ไปตกอยู่ที่อินเทอร์เน็ตของโรงแรมเอง ไม่ผ่าน VPS เลย แต่ เมื่อต่อตรงไม่สำเร็จ (ลูกค้าอยู่หลัง NAT/CGNAT เข้มงวด) จะ fallback มาใช้ relay กลาง ซึ่งถ้ารันอยู่บน VPS หลักก็จะกินbandwidthส่วนนั้นเหมือนกัน — เหตุผลคือ edge server ที่โรงแรมถูกซ่อนหลัง Tailscale โดยตั้งใจ (ไม่เปิด port ออก public internet) มือถือลูกค้าที่ไม่ได้อยู่ใน Tailscale network เดียวกันจึงต่อตรงไม่ได้เสมอไป

2. แผน Scale Server ที่เตรียมไว้ล่วงหน้า

แผนนี้ใช้ได้ทั้งสองกรณี — เตรียมไว้เพื่อไม่ต้องตัดสินใจกะทันหันตอนระบบโตจริง:

เฟสเงื่อนไขที่ต้องขยับสิ่งที่ต้องทำ
เฟส 0 — ปัจจุบันยังไม่มีวิดีโอไหลผ่าน VPS (เชื่อมตรงผ่าน LAN)ไม่ต้องทำอะไรเพิ่มด้าน bandwidth
เฟส 1เริ่มมีโรงแรมต้องการให้ลูกค้าดูจากนอกสถานที่ติดตั้ง Mini Hub ให้โรงแรมนั้น (แนะนำ) แทนการเปิดผ่าน VPS กลาง
เฟส 2เลือกไหลผ่าน VPS กลาง และคนดูพร้อมกัน > 10 สายอัปเกรด VPS ตามตารางขั้นบันไดด้านบน
เฟส 3ต้องเพิ่ม backend มากกว่า 1 เครื่องพร้อมกันย้าย rate limiter จากหน่วยความจำเครื่องเดียวไป Redis (มี Redis ใช้งานอยู่แล้วสำหรับ AI job queue — ต่อยอดได้ทันที)
เฟส 4ระบบโต > 50–100 โรงแรมที่ใช้งานจริงแยกเครื่อง media relay ออกจาก backend หลัก ไม่ให้ปนกัน

ฐานข้อมูล (Postgres + pgvector) รองรับ scale ระดับ startup ได้อีกนาน ยังไม่ต้องวางแผน replica/cluster ในเฟสนี้ (ตามหัวข้อ 5.1 เอกสารเดิม)

ตัวเลขทั้งหมดในเอกสารนี้เป็นการประมาณการเพื่อวางแผนงบเบื้องต้น ปรับค่าตั้งต้นได้ที่ช่องกรอกด้านบน — ก่อนใช้ตัดสินใจเชิงธุรกิจจริง แนะนำ (1) วัด bitrate จริงของกล้องด้วย ffprobe แทนตัวเลขประมาณอุตสาหกรรม และ (2) เก็บข้อมูลยอดจอง/ค่าเช่าห้องพักจริงจากโรงแรมที่ใช้งานอยู่ แทนค่าสมมติฐาน 15,000 บาท/เดือน/โรงแรม ที่ตั้งไว้เป็นค่าเริ่มต้น
